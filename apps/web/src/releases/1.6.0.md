# Sakuya 1.6.0

### Breaking
- **All configuration now lives in one file, `sakuya.config.json`.** Settings used to be spread across a root `.env` that the server never actually loaded, a second `apps/server/.env`, and values hardcoded in the web build. So changing the port broke the web proxy, and resource limits set in `.env` silently did nothing. The file is created on first start and **migrates your old `.env` automatically**, so the port, data dir and login carry over. You can delete the `.env` files afterwards. `sakuya.config.example.json` shows every setting, and editors get autocomplete from its schema. An invalid value now stops startup and names the key, instead of quietly falling back to a default.
- **Environment variables are no longer read outside Docker.** A `PORT`, `SAKUYA_HOST` or `AUTH_ENABLED` in your shell is ignored; set `server.host`, `server.port` and `auth.enabled` in the file instead. As a safety net, if an old `AUTH_ENABLED=true` is still around and the file disagrees, Sakuya refuses to start rather than coming up without a password. **Docker users:** `SAKUYA_*` variables still override the file inside the container. Machine-specific mounts, ports and limits now belong in a `docker-compose.override.yml`, since `docker-compose.yml` is now generic.
- The per-subsystem knobs `SAKUYA_JOB_CONCURRENCY`, `SAKUYA_FFMPEG_THREADS`, `SAKUYA_ONNX_THREADS`, `SAKUYA_SHARP_CONCURRENCY` and `SAKUYA_HARD_LIMIT` are gone. `limits.cpus` derives all of them.

### Added
- **CPU and memory limits outside Docker.** Set `limits.cpus` and `limits.memory` in the config file. The CPU budget sizes job concurrency, ffmpeg, the tagger and image processing together. The memory cap is enforced as a hard ceiling: through a systemd scope on Linux and a job object on Windows. The boot log reports what is actually enforced, so a limit that couldn't be applied says so instead of booting cleanly.
- **Unreachable folders keep their media.** If a scan finds a library folder empty and every file it indexed there missing, that looks like an unmounted drive or a missing Docker volume, not a deliberate deletion. The folder is now flagged and its tags, likes and watch history are kept. It used to wipe them. A folder you really emptied can be detached from its library.

### Improved
- **The AI tagger gives back its memory when idle.** The model holds about 800 MB. It is now unloaded after a minute without use and reloads in a second or two when needed. On Linux the freed memory is actually returned to the OS; before, most of it stayed with the process.
- **Liking something no longer refetches every list.** A heart click used to reload every page of every grid you'd scrolled through. It now updates the item in place, including on the Discover feed, which previously kept showing the old state.
- **Discover pages are cheaper.** Taste scores are computed once per profile instead of on every page.
- Video watch time is saved every 10 seconds instead of every second, and any unsaved time is sent when you move to the next item.
- Faster database writes, and requests wait for a running scan to finish writing instead of failing with "database is busy".

### Fixed
- **Stepping through videos no longer grows the tab's memory.** A replaced video player, especially a looping one, kept downloading and holding its buffer in the background. Players are now torn down when you move on.
- Discover sometimes repeated or skipped items while scrolling, because liking something or playing a video re-ranked the feed mid-scroll. A scroll now finishes on the ordering it started with.
- Deleting media left tag counts stale, so the tag sidebar kept offering tags with no remaining media. It also left transcoded videos on disk. All delete paths now share one cleanup, run as a single transaction.
- `.ts` files are only indexed if they are really video (MPEG transport streams). TypeScript files, such as the ones in Wallpaper Engine workshop folders, are skipped.
- Two requests for the same missing thumbnail could generate it twice and send a half-written file. Thumbnails are now generated once and swapped into place atomically.
- A file replaced with different content under the same name kept its old AI tags and transcode. It's now re-tagged and re-transcoded on the next scan.
- Deleting a library while a download into it was still running could crash the server.
- Deleting a whole download batch could leave its media in the library.
- Long transcodes no longer build up ffmpeg's entire log output in memory.
- A library at a filesystem root (`/` or `C:\`) was not recognized as containing its own files.
