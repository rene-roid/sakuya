# Setup Guide

## Prerequisites

- [Bun](https://bun.sh) — package manager and runtime for both install and dev.

## Getting started

```bash
bun install     # installs deps for all workspaces (apps/*, packages/*)
bun dev         # starts server (:3777) and web (:5173) together
```

Or use the bundled scripts, which install Bun for you if it's missing:

```bash
./setup.sh   # or setup.bat on Windows
./run.sh     # or run.bat
./update.sh  # git pull + reinstall deps
```

Open `http://localhost:5173`. The Vite dev server proxies `/api` to the backend.

Useful variants: `bun dev:server`, `bun dev:web`, `bun typecheck`, `bun build`.

## Workspace layout

```
apps/server/   Bun + Express backend (routes/, services/, db/)
apps/web/      React + Vite frontend (routes/, components/, hooks/, lib/)
packages/shared/  Types/utils shared between server and web
docker/        nginx config for the container build
```

## Folders you shouldn't touch by hand

| Path | What it is | Why leave it alone |
|---|---|---|
| `apps/server/data/` | Runtime data dir: SQLite DB (`tbge.db*`), `thumbnails/`, `transcodes/`, `uploads/`, `models/` (ONNX tagger), `downloader/` (gallery-dl bin + cookies) | Live user data and a live SQLite file (plus `-wal`/`-shm` sidecars). Editing/deleting while the server runs can corrupt the DB or drop real libraries. Gitignored — don't try to commit it. Override the location with `server.dataDir` in `sakuya.config.json`, or move it to `~/.sakuya` from Settings > System — don't move it manually. |
| `node_modules/` (root and per-workspace) | Installed deps | Managed by `bun install`. Never hand-edit; delete and reinstall if something's wrong. |
| `apps/web/dist/` | Vite build output | Regenerated by `bun build`. Not source. |
| `bun.lock` | Dependency lockfile | Only changes via `bun install`/`bun add`; hand-editing desyncs it from `node_modules`. |
| `.idea/`, `.junie/`, `.impeccable/` | Editor/tool-specific state (JetBrains, Junie, Impeccable hook cache) | Local tool metadata, not project source. Gitignored (except `.idea` is partially tracked — check before deleting). |
| `tray/` | Currently empty scaffold dir | Not wired to anything yet; nothing to run there. |

Anything under `apps/server/data/` is the one place that holds actual user state (your media library metadata, tags, downloaded files). Back it up before any destructive experiment; everything else here is regeneratable from source.

## Configuration

Everything is configured in one file, **`sakuya.config.json`** at the repository root. It is created
with the defaults the first time Sakuya starts (or by `./setup.sh`), is gitignored, and is read by
the server, the web dev server and the Docker containers alike. Every key is optional. Restart after
editing it.

The committed [`sakuya.config.example.json`](../sakuya.config.example.json) is the same file with
every setting at its default — copy it to `sakuya.config.json` to start by hand. Your own
`sakuya.config.json` never leaves your machine.

```json
{
  "$schema": "./packages/shared/sakuya.config.schema.json",
  "server": { "port": 3777, "host": "127.0.0.1", "dataDir": null, "https": false },
  "web": { "port": 5173 },
  "auth": { "enabled": false, "secret": "" },
  "limits": { "cpus": null, "memory": null }
}
```

The `$schema` line gives VS Code and JetBrains editors autocomplete and a description of each
setting on hover.

| Setting | Default | Purpose |
|---|---|---|
| `server.port` | `3777` | API server port. The web dev server proxies `/api` to it, so changing it here is enough. |
| `server.host` | `127.0.0.1` | Interface the API **and** the web dev server bind to. Loopback by default, so a fresh install isn't exposed to the network: the server serves your whole library and can open a file manager on the host. Set `0.0.0.0` to reach Sakuya from other machines — turn `auth` on first. |
| `server.dataDir` | `null` | Where the DB, thumbnails, uploads and models live. `null` autodetects: `~/.sakuya` if it exists, else `apps/server/data`. A relative path is relative to the config file. Setting it disables the in-app move in Settings > System. |
| `server.https` | `false` | Marks the login cookie `Secure`. Only with HTTPS in front: a `Secure` cookie is silently dropped over plain HTTP, which is a supported LAN setup. |
| `web.port` | `5173` | Port of the web interface (the Vite dev server). |
| `auth.enabled` | `false` | Require a password. |
| `auth.secret` | `""` | The password; required when `auth.enabled` is on. Changing it signs every session out. |
| `limits.cpus` | `null` | CPU budget in cores, fractions allowed. See [Resource limits](#resource-limits). |
| `limits.memory` | `null` | Memory ceiling: `"2g"`, `"512m"`, or a byte count. See [Resource limits](#resource-limits). |

A value of the wrong type stops Sakuya at startup with the file and key named, rather than quietly
falling back to a default. An unknown key (most likely a typo) is logged and ignored.

**Environment variables are not read outside Docker.** One file is the whole story; a `PORT` or
`AUTH_ENABLED` left in your shell or an old `.env` is ignored, and the boot log says so.

### Upgrading from `.env`

The first start after upgrading creates `sakuya.config.json` from your old `.env`, `apps/server/.env`
and environment, so the port, data dir and login carry over, then logs what it did. Delete the
`.env` files afterwards. As a safety net, if an old `AUTH_ENABLED=true` is still around while the file
has `auth.enabled` off, Sakuya refuses to start rather than come up without a password. The old
per-subsystem knobs (`SAKUYA_JOB_CONCURRENCY`, `SAKUYA_FFMPEG_THREADS`, `SAKUYA_ONNX_THREADS`,
`SAKUYA_SHARP_CONCURRENCY`, `SAKUYA_HARD_LIMIT`) are gone; `limits.cpus` derives all of them.

### Docker

`docker-compose.yml` mounts the same `sakuya.config.json` into the server container, so create it
before `docker compose up` (`cp sakuya.config.example.json sakuya.config.json`, or `./setup.sh`). A
missing file is an error on purpose — Docker would otherwise create an empty *directory* in its place.

Docker is the only place settings can be overridden: a `SAKUYA_*` variable under `environment:` in
compose wins over the file.

| Variable | Overrides |
|---|---|
| `SAKUYA_PORT`, `SAKUYA_HOST`, `SAKUYA_DATA_DIR` | `server.port`, `server.host`, `server.dataDir` — already pinned by the image to `3777`, `0.0.0.0` and `/data`, which is container plumbing |
| `SAKUYA_HTTPS` | `server.https` |
| `SAKUYA_AUTH_ENABLED`, `SAKUYA_AUTH_SECRET` | `auth.enabled`, `auth.secret` |
| `SAKUYA_MAX_CPUS`, `SAKUYA_MAX_MEMORY` | `limits.cpus`, `limits.memory` |

Ports the containers publish, the data folder and your media folders are compose's concern. Put
anything specific to your machine — media mounts especially — in a `docker-compose.override.yml`
next to it, which compose merges in automatically and git ignores.

## Resource limits

Two settings, `limits.cpus` and `limits.memory`, and Sakuya applies them in two layers:

**In-app sizing (everywhere).** The CPU budget decides how many background jobs run at once and how
many threads ffmpeg, onnxruntime and libvips each spawn under them. That matters even under a hard
cap: those libraries size their pools from the core count they can *see*, which inside a quota is
still every core on the host, and they would then fight over the share they actually get. At
`cpus: 2` this reproduces the constants the deployment was originally tuned with
(`apps/server/src/limits.test.ts` pins it). With no budget, the old defaults apply. Peak memory is
roughly concurrency × per-task peak, so a lower CPU budget also lowers the worst case for memory.

**A hard ceiling, enforced by the kernel.** A process can't impose one on itself, so the launcher
(`apps/server/src/launch.ts`, which `bun dev`, `bun run start`, `run.sh` and `run.bat` all use) puts it
in place before the server starts. It wraps only the server, not the web dev server:

| Platform | Mechanism | Notes |
|---|---|---|
| Linux | transient systemd scope with `MemoryMax` / `CPUQuota` | Needs systemd, with the controller delegated to your user. Memory usually is; cpu sometimes isn't. Each limit is tried separately, so one being refused doesn't cost the other. |
| Windows | job object (memory limit + hard CPU-rate cap) | Everything the server spawns, ffmpeg included, inherits it. |
| macOS | none | In-app sizing only. |
| Docker | the container's `cpus` / `mem_limit`, set in `docker-compose.yml` or your `docker-compose.override.yml` | The app detects the CPU quota and sizes itself to it, so there's nothing to repeat in `sakuya.config.json`. |

Past the memory ceiling, allocations fail (the process is OOM-killed on Linux), the same as Docker's
`mem_limit`. `--max-old-space-size` would not be a substitute: most of this app's memory is not JS
heap but libvips buffers, onnxruntime arenas, ffmpeg children and SQLite page cache.

The launcher and the server's boot log both state what is actually enforced, not what was asked
for. A `limits.memory` that isn't binding says `NOT enforced` out loud, instead of a clean boot
implying a cap that isn't there:

```
[sakuya] Hard limits via systemd: memory 2.0 GiB, 2 CPUs
Limits: 2 CPUs (config) -> 2 concurrent jobs, ffmpeg 1, onnx 2/1, libvips 2; memory capped at 2.0 GiB
```
